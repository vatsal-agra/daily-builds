# Keyhole — TLS 1.3 from scratch (Go)

A complete **TLS 1.3 (RFC 8446)** implementation whose protocol logic is hand-written: record layer,
HKDF key schedule, handshake codecs, client and server state machines, HelloRetryRequest, alerts,
PSK resumption, KeyUpdate, mutual TLS — plus a CLI and a **decrypting TLS inspector** that reads a
key log and shows you every handshake message and application byte of a live session.

Only *primitives* come from the Go standard library (AES-GCM, SHA-2, X25519/P-256, ECDSA/Ed25519/RSA-PSS,
`crypto/x509`). ChaCha20-Poly1305 is written from RFC 8439. The library never imports `crypto/tls`;
that, OpenSSL, curl and Python's `ssl` are used purely as **independent oracles**.

## Run it

```bash
./verify.sh                      # build, vet, 67 tests under -race, 5 fuzzers, 44 CLI/interop assertions
go build -o keyhole ./cmd/keyhole

./keyhole certgen -dir pki                                   # CA + server + client certs
./keyhole server -cert pki/server.pem -key pki/server.key -keylog keys.log &
./keyhole client -connect 127.0.0.1:8443 -ca pki/ca.pem -trace -resume 1
curl --cacert pki/ca.pem https://localhost:8443/            # interoperates with curl / openssl / Python

# see inside a session without a MITM certificate:
./keyhole inspect -listen :9443 -upstream 127.0.0.1:8443 -keylog keys.log -data 80 -html timeline.html
./keyhole client -connect 127.0.0.1:9443 -servername localhost -ca pki/ca.pem -keylog keys.log
```

Library use:

```go
c, err := tls13.Dial("example.com:443", &tls13.Config{RootCAs: pool, SessionCache: tls13.NewSessionCache()})
```

## Features

**Protocol**
- Key schedule (early/handshake/master ladder, traffic keys, Finished, resumption PSK, exporter RFC 8446 §7.5), `SSLKEYLOGFILE` output
- Record layer: inner content type + padding (`RecordPadBlock`), per-record nonces, fragmentation both ways, 16 KiB limits, compat CCS
- Full 1-RTT handshake, client and server; cipher suites AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305
- Key exchange X25519 + P-256 (small-order / invalid-point rejection); **HelloRetryRequest** (+ cookie echo)
- Certificates: ECDSA P-256/P-384, Ed25519, RSA-PSS; chain + hostname/IP verification, SNI (`GetCertificate`), ALPN
- **PSK resumption** with stateless AES-GCM-sealed tickets, binders, HRR+PSK; resumed sessions re-verify the server chain and keep client identity
- **KeyUpdate** both directions, automatic after N records, flood-limited
- **Mutual TLS** (`RequestClientCert` / `RequireClientCert`)
- Alerts: correct code per failure; fatal-alert handling; close_notify; truncation detection (`ErrTruncated`)
- Deadlines: read timeouts are retryable; `Close` never hangs behind a stuck writer

**Tools**
- `keyhole inspect` — transparent proxy + key log → decoded, decrypted timeline (terminal and self-contained HTML), follows KeyUpdates; works on logs written by OpenSSL/curl/Go too
- `keyhole certgen|server|client|get`
- Native Go fuzzers for every parser, the record layer and live client/server streams

## How it is verified (independent oracles)

| Check | Oracle |
|---|---|
| Every traffic secret, both directions, all suites, 4 key types | line-for-line against key logs from `crypto/tls` **and** OpenSSL |
| Exporter output | `openssl s_client -keymatexport` |
| ChaCha20-Poly1305 | RFC 8439 vector + 308 random vectors generated by Python `cryptography` |
| HKDF / key-schedule constants | RFC 5869 A.1; known TLS 1.3 early-secret / `derived` values |
| Handshake, resumption, KeyUpdate, mTLS, HRR | `crypto/tls`, `openssl s_server/s_client`, `curl`, Python `ssl` — both directions |
| Hostile peers | 24 malformed-ClientHello cases, 15 hostile-server cases, tamper/replay/truncation proxy, 5 fuzzers |

See [REVIEW.md](REVIEW.md): an independent adversarial review found a **resumption certificate-verification bypass**
and an **mTLS ticket bypass**, among 13 issues — all fixed with regression tests.

## Why I built this today

The repo already has DNS, TCP, a DHT, crypto primitives and a torrent client — every one of which
travels over a channel nothing in the repo had ever built. TLS 1.3 is also an unusually *checkable*
problem: OpenSSL and Go sit in the sandbox, key logs let you compare secrets byte-for-byte, and a
wrong implementation simply fails to interoperate. That makes "it works" falsifiable.

## Honest limits

No 0-RTT/early data (so tickets have no anti-replay store), no TLS ≤1.2, no OCSP/SCT, no P-384/ML-KEM
key exchange, no `rsa_pkcs1`/`rsa_pss_pss` signature schemes, not constant-time audited (the primitives are
the stdlib's; my Poly1305/ChaCha20 are straightforward and not hardened against side channels), and
RFC 8448's byte-level trace could not be fetched offline. **Do not use this to protect real data.**

## Where a human could take this next

- 0-RTT with a single-use ticket store and replay window (the missing half of resumption)
- Post-quantum hybrid `X25519MLKEM768` key share; P-384/X448 groups
- OCSP stapling, `certificate_authorities`, post-handshake client auth, record_size_limit
- Constant-time/side-channel review of the hand-written ChaCha20-Poly1305; assembly-speed Poly1305
- Feed the inspector pcap files; add a Wireshark-style hex view
- A QUIC-TLS mode (the handshake layer is already separated from the record layer)
