# Adversarial review

Hostile pass over `veil/`, treating myself as the attacker: can a prover
who does NOT know a witness get accepted? Can a caller misuse the API to
silently defeat a security property the protocol is supposed to guarantee?
Does anything hang, crash, or silently produce a wrong answer on realistic
bad input? Every finding below was reproduced with a concrete script before
being written down, and every one is fixed (see "Fix" + `tests/` for the
regression test that would have caught it).

## Finding 1 (critical) — degenerate public keys break soundness completely

`schnorr.verify`, `fiatshamir.verify`, and `orproof.verify_or` all accept
any integer as a "public key" `y` and just plug it into
`g^s == t * y^c mod p`. Nothing checks that `y` is actually a member of the
order-`q` subgroup generated by `g`.

That matters because `p` is a *safe* prime, so `Z_p^*` has order `2q` and
contains an element of order exactly 2 (namely `p - 1`, since `(p-1)^2 =
1 mod p`) that is **not** in `<g>` (q is an odd prime, so no element of
order 2 divides into a subgroup of order q). A prover who registers
`y = p - 1` as their "public key" — for which no discrete log relative to
`g` even exists — can still fool an *honest* verifier issuing genuinely
random challenges roughly **half the time**, not with negligible
probability `~1/q` as soundness requires:

```
cheating prover with NO real witness fooled the verifier in 9912/20000 = 0.4956
of honest random challenges (soundness should guarantee this is ~1/q)
```

The exploit: since `y` has order 2, `y^c mod p` collapses to just `1` or
`y` depending only on the parity of `c`. Whenever the verifier's random
challenge happens to be even, the prover can satisfy the equation using the
*trivial* opening `s = r` (as if proving `x = 0`) — no real witness needed.
This is exactly the "invalid-subgroup" pitfall that shows up as small-
subgroup/invalid-curve attacks in real Diffie-Hellman and ECDH
implementations, reproduced here in the Schnorr identification setting.

**Fix**: added `group.is_valid_group_element`, requiring `1 < y < p - 1`
and `y^q == 1 mod p` (real membership in the order-q subgroup, and no
degenerate identity key). `schnorr.verify`, `fiatshamir.verify`, and
`orproof.verify_or`/`prove_or` now reject any key that fails this check
before doing anything else. Regression test: `test_schnorr.py::
test_degenerate_public_key_rejected` reproduces the exact exploit above and
asserts it is now rejected outright (not just "usually" — every single
attempt, since the check is unconditional).

## Finding 2 (high) — nonces default to a non-cryptographic PRNG

Every "give me a fresh secret" call (`group.random_exponent`,
`schnorr.generate_keypair`/`commit`, `fiatshamir.sign`, `orproof.prove_or`)
fell back to a bare `random.Random()` when no `rng` was supplied. Python's
`random` module is a Mersenne Twister: its full internal state is
recoverable from ~624 consecutive outputs, after which every future (and
past) output is predictable. For a system whose entire security rests on
per-proof nonces being unpredictable, that is the exact class of bug behind
real-world catastrophic key recovery (the Sony PS3 ECDSA fixed-nonce break,
and multiple Bitcoin-wallet key thefts from weak Android `SecureRandom`
seeding, are the canonical examples this generalizes from — the specific
angle here is *predictability*, not literal reuse, but a predictable Schnorr
nonce is exactly as fatal as a reused one, since `x = (s1 - r) * c^-1 mod q`
falls straight out the moment `r` is known or guessable).

**Fix**: every default-RNG fallback (`rng = rng or random.Random()`) is now
`rng = rng or secrets.SystemRandom()` — `secrets.SystemRandom` is a drop-in
`random.Random` subclass (same `.randrange`/`.shuffle`/`.randbytes` API)
backed by `os.urandom` for every single call, with no recoverable internal
state. A caller can still pass an explicit `random.Random(seed)` for
reproducible demos and tests (every CLI subcommand's `--seed` flag, and the
whole test suite, does exactly that) — but that is now something a caller
has to opt into, not the silent default.

## Finding 3 (medium) — `generate_safe_prime_group` hangs on tiny `bits`

```
$ timeout 5 python3 -c "from veil.group import generate_safe_prime_group; \
    generate_safe_prime_group(bits=2, seed=1)"
exit code: 124   # killed by timeout — genuinely hangs forever
```

For `bits=2`, the candidate-construction line forces both the top bit and
the low (odd) bit into the *same* single bit position, so `q` is pinned to
the constant `1` on every iteration — which is never prime, so the search
loop never terminates. This isn't just a theoretical edge case: it is one
`--bits 2` typo away from a hung CLI process.

**Fix**: `generate_safe_prime_group` now raises `ValueError` for
`bits < 8` (8 bits is already comfortably past where this degenerates, and
below any bit length anyone would use for an actual group) instead of
looping forever. The existing top-level CLI exception handler turns that
into a clean one-line error message and a non-zero exit code, no hang.

## Finding 4 (medium) — coloring round nonces bypass the seeded RNG

`coloring.commit_round` calls `commit.commit(bytes([c]))` with no explicit
nonce, so `commit()` falls back to drawing the nonce straight from
`os.urandom` — completely ignoring the `rng` parameter the round was given.
Two consequences: (1) the same `--seed` produces a *different* transcript
every run, silently breaking the reproducibility every other command in
this toolkit provides, and (2) the protocol's randomness is split across
two unrelated sources for no reason, which makes it harder to reason about
and impossible to fully drive from a single seeded `rng` in tests.

**Fix**: `commit_round` now draws each nonce via `rng.randbytes(NONCE_BYTES)`
and passes it explicitly into `commit()`. The whole protocol run is now
reproducible end-to-end from one `rng`, and still cryptographically sound
by default because of Finding 2's fix (the default `rng` is
`secrets.SystemRandom`, whose `.randbytes` is still OS-entropy-backed).

## Finding 5 (medium) — a committed coloring round can be opened twice

Nothing stopped a caller from calling `open_round(graph, state, edge_a)`
and then `open_round(graph, state, edge_b)` again on the *same*
`RoundCommitState` with a second, different edge index. The entire
soundness/zero-knowledge argument for this protocol depends on committing
to a fresh random relabeling and opening **exactly one** edge per round —
revealing two edges' worth of colors from a single permutation leaks
strictly more about the real coloring than the protocol is supposed to
allow (in the limit, opening enough edges from one committed permutation
recovers the whole permuted coloring, at which point there is no zero-
knowledge property left at all).

**Fix**: `RoundCommitState` now tracks whether it has already been opened
and `open_round` raises `RuntimeError` on a second call against the same
state. `run_round`'s single-round-per-state usage pattern already matched
this; the fix makes misuse impossible instead of merely "not how the demo
happens to call it."

## Finding 6 (low) — witness extraction trusts its input blindly

`schnorr.extract_witness` computed `x = (s1-s2)*(c1-c2)^-1 mod q` from
whatever two transcripts it was handed, without ever checking that either
transcript actually verifies. Fed two unrelated/garbage transcripts that
happen to share a `t`, it silently returns a number that *isn't* a witness
for anything, with no error — a footgun for any caller outside the one
curated call site the original demo used.

**Fix**: `extract_witness` now takes the public key `y` and verifies both
transcripts accept against it before extracting, raising `ValueError`
immediately if either does not (or if `t` differs / `c` matches, the two
pre-existing checks). `tests/test_schnorr.py::test_extract_rejects_bad_transcripts`
covers all four ways this can go wrong.

## Investigated, not a bug

- **Fiat-Shamir hash framing (`str(t).encode() + b"|" + context`)**: could
  two different `(t, context)` pairs hash to the same bytes? No — `str(t)`
  is always a pure ASCII digit string containing no `|` byte, so the first
  `|` in the concatenation unambiguously marks the end of `t`'s encoding;
  two different `t` values can never produce the same prefix, so no
  collision is possible through this framing.
- **Key-substitution in Fiat-Shamir signatures** (not hashing `y` into the
  challenge): for a *fixed* `(t, s, message)` (hence fixed `c`), the
  verification equation `y^c == g^s * t^-1 mod p` has exactly one solution
  `y` (because `c != 0 mod q` is invertible and the map `y -> y^c` is a
  bijection on the order-q subgroup) — so a signature can never be
  transplanted onto a different public key for the same message. Standard,
  fine.
- **OR-proof with N=1**: reduces to plain Fiat-Shamir Schnorr (the "sum of
  other challenges" is an empty sum = 0, so the real branch's challenge is
  the full Fiat-Shamir hash) — checked directly in
  `test_orproof.py::test_or_proof_single_member`.
- **Empty/degenerate graphs**: `Graph.__post_init__` already rejects
  self-loops and out-of-range vertex indices at construction time; an
  edgeless graph correctly makes `challenge_edge` raise (nothing to
  challenge) rather than doing anything silently wrong, and
  `soundness_error_bound(0, rounds)` explicitly returns `1.0` (no edges
  means no way to ever catch a cheating prover, which is the true answer,
  not a special-cased hack).
- **Out-of-range-but-arithmetically-fine integers** (e.g. `y > p` or
  negative `y`) passed as a public key: Python's three-argument `pow()`
  reduces the base mod `p` internally, so these behave identically to
  their reduced form — not a distinct bug from Finding 1, and not a way to
  bypass the subgroup-membership fix (reducing mod `p` first, then
  checking `y^q == 1 mod p`, gives the same answer either way).

## Gate check

After the fixes above, the exploit script from Finding 1 (20,000 trials
against a degenerate public key) now shows **0/20000** successes — full
rejection, every time, not merely a lower rate — and the full pytest suite
plus `demo.sh` (Phase 5) both pass. Re-running the exact repro commands
quoted above for every finding now behaves as documented in each "Fix".
